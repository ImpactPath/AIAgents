# MCP 커넥터 제작 시행착오 분석과 제작 가이드라인

YouTube Subtitles 웹앱을 Claude용 MCP(Model Context Protocol) 커넥터와 MCP 앱(채팅 안에 그려지는 메뉴 카드)으로 확장하는 과정에서 겪은 시행착오를 정리하고, 다음에 비슷한 것을 만들 때 같은 실수를 피하기 위한 가이드라인으로 묶은 문서입니다. 클라우드 배포에서 겪은 문제는 `DEPLOYMENT_NOTES.ko.md`에 따로 있으므로 여기서는 MCP와 호스트(Claude Desktop, claude.ai 웹) 관련 문제에 집중합니다.

## 1. 한 줄 결론

시행착오의 대부분은 코드 오류가 아니라 세 가지 잘못된 가정에서 나왔습니다. 첫째, 호스트(Claude 앱)가 규격대로 동작할 것이라는 가정. 둘째, 모델이 안내문을 매번 같은 방식으로 따를 것이라는 가정. 셋째, 상태(누가 무엇을 조회했는지)를 어디에 두어야 하는지에 대한 가정입니다. 따라서 다음 프로젝트에서는 기능을 만들기 전에 호스트에서 최소 예제를 먼저 돌려 보고, 판단은 모델이 아니라 서버가 하도록 설계하며, 상태는 세션이나 화면이 아니라 서버 프로세스에 두는 것이 핵심입니다.

## 2. 시행착오 목록

시간순으로 정리했습니다. 각 항목의 "교훈"이 4절 가이드라인의 근거입니다.

| 번호 | 증상 | 실제 원인 | 해결 | 교훈 |
| --- | --- | --- | --- | --- |
| 1 | 링크를 주면 확인 없이 자막을 바로 내려받음 | 도구가 조회와 다운로드로만 나뉘어 있어 모델이 곧장 다운로드를 호출 | 메뉴 우선 흐름 설계, 선택지를 조회 결과에 포함 | 사용자 확인이 필요한 흐름은 도구 구조로 강제해야 함 |
| 2 | 메뉴 카드가 전혀 나타나지 않음 | Desktop은 커넥터 도구를 키워드 검색으로 지연 로드하는데, 메뉴 전용 도구 `subtitle_menu`는 검색어에 걸리지 않아 모델이 존재조차 몰랐음 | 메뉴 화면을 주 도구 `get_video_info`에 직접 묶음 | 호스트가 도구를 어떻게 찾는지 먼저 확인. 화면은 어차피 호출되는 도구에 붙일 것 |
| 3 | 모델이 `get_video_info`를 건너뛰고 자막을 가져감 | 안내문만으로는 순서를 강제할 수 없음 | `user_confirmed` 인자와 서버 게이트(조회 전에는 거부) 추가 | 안내문은 권고, 서버 검사는 강제. 중요한 순서는 서버가 검사 |
| 4 | 클라이언트 기능(앱 지원 여부)을 서버가 모름 | 무상태 HTTP 모드에서는 초기화 정보가 요청마다 사라짐 | 세션 유지 모드(`Mcp-Session-Id`)로 전환 | 클라이언트 기능에 따라 분기하려면 세션이 필요 |
| 5 | 링크를 주면 메뉴 대신 모델이 자체 질문 카드를 띄움 | 안내문에 "메뉴를 그리는 클라이언트면 도구 먼저, 아니면 질문 먼저"라는 조건이 있었는데 모델은 자기 클라이언트 종류를 모름 | 조건을 없애고 무조건 `get_video_info`를 먼저 부르게 함. 다음 단계는 서버가 결과 텍스트로 알려줌 | 모델에게 판단을 맡기지 말 것. 안내문은 조건 없는 명령문으로 |
| 6 | 링크만 보내면 "Your connectors" 카드가 뜨고 멈춤. "Use"를 눌러도 아무 일 없음 | Desktop은 화면을 그리는 도구를 서드파티 앱으로 분류해 대화마다 옵트인을 요구함. 도구 검색 결과의 `[third_party_mcp_app]` 표시와 호스트 규칙 문구로 확인 | 첫 메시지에 커넥터 이름을 함께 쓰면 즉시 실행. 서버에서는 우회 불가 | 호스트 정책은 서버로 못 이김. 사용법으로 흡수하고 문서에 적을 것 |
| 7 | "채팅에 넣기"가 성공 표시를 내는데 모델은 자막을 모름 | Desktop이 `ui/update-model-context`를 받아 주지만 모델에게 전달하지 않음 | `ui/message`로 자막 전문을 입력창에 넣고 사용자가 전송하게 변경 | 규격에 있어도 호스트가 실제로 반영하는지 확인. 모델이 봐야 하는 내용은 메시지로 |
| 8 | 브라우저 claude.ai에서 미리 보기와 다운로드가 "조회 먼저 하라"는 오류 | 메뉴 카드의 도구 호출이 모델의 조회와 다른 MCP 세션으로 도착해 세션별 게이트가 거부 | 조회 기록을 프로세스 전역으로 변경 | 화면과 모델이 같은 세션을 쓴다고 가정하지 말 것. 상태는 프로세스 전역에 |
| 9 | 요약 버튼의 조건문("이미 대화에 있으면 쓰라")이 사라짐 | 조건문 여부를 카드 안 메모리에 두었는데 카드는 조회마다 다시 그려져 메모리가 사라짐 | 모든 요청문을 조건문으로 통일, 상태 없이 동작 | 화면 안에 상태를 두지 말 것. 판단은 대화를 볼 수 있는 모델에게 |
| 10 | 다운로드 파일 이름이 퍼센트 부호로 깨짐 | 호스트가 파일 이름의 비ASCII 문자를 URL 인코딩 | 파일 이름을 ASCII로 정리 | 호스트에 넘기는 이름은 ASCII 안전하게 |
| 11 | 요약 등 버튼이 바로 실행되지 않고 입력창만 채움. 빨간 경고 배너 | Desktop 정책: 앱이 채운 메시지는 사용자가 전송해야 하고 경고를 항상 붙임 | 정상 동작으로 문서화 | 호스트의 보안 정책은 설계 전제로 |
| 12 | 다운로드 결과나 첨부 리소스가 채팅에 파일 카드로 안 보임 | Desktop이 커넥터의 리소스 첨부를 카드로 표시하지 않음 | 다운로드는 저장으로, 파일 목록 등록은 모델에게 지시하는 문구로 대체 | 파일 표시 방식은 호스트마다 다름. 대안 경로를 함께 둘 것 |
| 13 | "왜 갑자기 안 되나"를 놓고 여러 번 추측 | 로그에 시각이 없어 화면의 현상과 대조 불가 | 로그에 시각 추가, 도구 호출과 클라이언트 접속을 기록 | 처음부터 시각과 호출 기록을 남길 것. 추측 전에 로그 |
| 14 | Mac 서비스 재등록이 I/O 오류로 실패 | `launchctl bootout` 직후 같은 이름으로 `bootstrap`하면 정리가 끝나기 전이라 실패 | 사라질 때까지 기다린 뒤 재시도 | 운영 스크립트는 타이밍 문제까지 흡수 |

## 3. 원인 유형별 분석

**호스트 동작이 문서와 다르거나 문서에 없음 (2, 6, 7, 8, 11, 12)**: 가장 많은 시간을 잡아먹은 유형입니다. 도구 지연 로드, 서드파티 앱 옵트인, 모델 컨텍스트 갱신 무시, 화면과 모델의 세션 분리는 모두 규격 문서로는 알 수 없고 실제 호스트에서 돌려 봐야 드러났습니다. 결정적 증거는 사용자가 Desktop의 도구 검색 단계를 펼쳐 보내 준 원문이었습니다.

**모델의 확률적 행동 (1, 3, 5)**: 같은 안내문으로도 대화마다 다른 선택을 합니다. 조건문이 있는 안내는 특히 위험했습니다. 해결은 두 가지였습니다. 순서를 서버가 검사하고, 안내문은 조건 없는 명령문으로 씁니다.

**상태를 둘 위치 (4, 8, 9)**: 세션에 두면 화면의 호출이 다른 세션으로 와서 깨지고, 화면에 두면 카드가 다시 그려질 때 사라집니다. 서버 프로세스 전역에 두고 사용자 확인은 명시적 인자로 받는 것이 가장 견고했습니다.

**운영 도구 (13, 14)**: 시각 없는 로그와 타이밍에 약한 스크립트는 문제 자체보다 진단 시간을 늘렸습니다.

## 4. MCP 커넥터 제작 가이드라인

### 4.1 시작 전: 호스트에서 최소 예제부터

1. 도구 하나와 빈 메뉴 카드만 있는 최소 서버를 만들어 실제로 쓸 호스트(Desktop, claude.ai 웹, 필요하면 Claude Code와 ChatGPT)에 연결합니다. 카드가 그려지는지, 도구가 검색되는지, 옵트인 카드가 뜨는지를 첫날에 확인합니다.
2. 서버 로그에 클라이언트 이름, 프로토콜 버전, 선언한 확장 기능, 도구 호출 이름을 시각과 함께 남깁니다. 이 로그가 이후 모든 진단의 출발점입니다.
3. 호스트가 규격의 어떤 기능을 실제로 반영하는지 목록으로 적어 둡니다. 이번에 확인된 것: Desktop은 `ui/message`, `ui/download-file`, `ui/open-link`, 전체 화면 표시 모드를 반영하고, `ui/update-model-context`는 받아 주지만 모델에 전달하지 않으며, 리소스 첨부를 파일 카드로 보여 주지 않습니다.

### 4.2 도구 설계

1. 도구 수는 최소로 하고, 이름과 설명에 사용자가 쓸 만한 키워드(youtube, subtitles, video 등)를 넣습니다. Desktop은 키워드로 도구를 찾습니다.
2. 사용자가 먼저 봐야 하는 화면은 어차피 첫 번째로 호출될 도구에 붙입니다. 화면 전용 도구는 호출되지 않습니다.
3. 첫 도구는 값싸고 부작용이 없게 만들고, 그 결과 텍스트에 "다음에 무엇을 할지"를 적습니다. 메뉴가 그려졌으면 기다리라고, 안 그려졌으면 무엇을 물으라고 서버가 정합니다.
4. 사용자 확인이 필요한 도구는 `user_confirmed` 같은 명시적 인자를 받고, 서버가 선행 조건(조회가 있었는지)을 프로세스 전역 기록으로 검사합니다. 세션별 검사는 화면의 호출이 다른 세션으로 올 수 있어 깨집니다.
5. 안내문(instructions)은 조건문 없이 씁니다. "링크가 오면 무조건 이 도구를 먼저 부르고, 결과가 오기 전에는 묻지 말고, 웹 도구로 페이지를 읽지 말라"처럼 해야 할 일과 하지 말 일을 명령문으로 적습니다.
6. 호스트가 옵트인 같은 절차를 요구할 수 있음을 안내문에 허용해 둡니다. "호스트가 먼저 동의를 요구하면 한 단계로 마치고 곧바로 도구를 부르라."

### 4.3 MCP 앱(화면) 설계

1. 화면은 상태를 갖지 않게 만듭니다. 카드는 도구 호출마다 새로 그려지고 새로 고침에도 사라집니다. 필요한 상태는 도구 결과에 담아 받습니다.
2. 모델이 반드시 봐야 하는 내용은 `ui/message`로 사용자 메시지에 넣습니다. 사용자가 전송해야 하고 경고 배너가 붙지만, 이것이 확실히 동작하는 유일한 경로였습니다.
3. 파일은 `ui/download-file`로 저장하게 하고, 파일 이름은 ASCII로 정리합니다. 채팅의 파일 목록에 올리고 싶으면 모델에게 "이 텍스트를 이 이름의 파일로 저장하라"는 문구를 메시지에 포함합니다.
4. 프롬프트 버튼은 결과 형식(구성, 개수, 언어, 금지 사항)을 요청문에 구체적으로 적습니다. "요약해줘" 한 마디보다 결과가 훨씬 안정적입니다.
5. 프롬프트는 "이미 대화에 있으면 그것을 쓰고 없을 때만 가져오라"는 조건문으로 시작해 재조회를 막습니다.
6. 표시 모드(전체 화면 등)는 호스트가 지원 목록에 넣었을 때만 버튼을 보입니다.
7. 화면은 단일 HTML 파일로 번들하고, 외부 스크립트 없이 호스트의 CSP 안에서 동작하도록 만든 뒤 Playwright 하네스로 호스트 흉내를 내어 자동 검증합니다.
8. 답변 언어는 호스트의 화면 언어가 아니라 "사용자가 써 온 언어"로 지정합니다. 화면 언어와 사용자의 언어는 다를 수 있습니다.

### 4.4 서버와 운영

1. 클라이언트 기능에 따라 분기하려면 세션 유지 모드를 씁니다.
2. 반복 호출이 예상되는 외부 자원(자막 본문 등)은 서버가 충분히 긴 시간(이번에는 1시간) 기억합니다.
3. 로그는 시각, 클라이언트 접속, 도구 호출 이름을 남깁니다. `healthz`에는 의존 서비스 상태를 포함합니다.
4. IP에 민감한 외부 서비스를 부르는 서버는 데이터센터가 아니라 집의 컴퓨터에서 돌리고 Tailscale Funnel 같은 터널로 공개합니다.
5. 설치 스크립트는 재실행이 안전하게, 타이밍 문제(launchd 정리 지연 등)를 흡수하게 만듭니다.
6. API 키는 헤더로 받고, 길이보다 무작위성을 요구하며, 교체 절차를 문서에 둡니다.

### 4.5 진단 방식

1. 추측보다 증거를 먼저 모읍니다. 서버 로그, 호스트의 도구 검색 결과 원문, 화면의 진행 기록이 가장 강력했습니다.
2. "갑자기 안 된다"는 현상은 코드 변경과 무관할 수 있습니다. 변경 이력과 실패 시각을 대조해 코드가 같았는지부터 확인합니다.
3. 가설은 한 번에 하나만 적용하고, 적용 뒤 같은 시나리오로 재현 여부를 확인합니다.
4. 호스트 정책으로 판명된 것은 고치려 하지 말고 사용법과 문서로 흡수합니다.

## 5. 다음 프로젝트 권장 순서
